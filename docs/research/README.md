## Applicability to the MVP

- The 0.5.0 transition research records temperature writes with the native preview flag kept enabled for short changes, and temperature writes with occasional brief preview activation for gradual changes. Brief activation asks Windows to apply the stored temperature. The research also covers explicit cleanup and one Night Light handle reused throughout the process. Its startup timestamp margin advances the first successful settings-write timestamp at least 699 seconds beyond the stored timestamp. This native flag differs from Circadia's schedule Preview playback. Circadia does not move timestamps backward, because the upstream probe found that temperature changes after a timestamp rewind were ignored, consistent with Windows ignoring timestamps at or below an inferred highest applied value. The same document records the watcher and snapshot contracts that observation and recovery use. Source findings and upstream display observations have separate limits. Controller integration and supported-host visual behavior remain implementation and release checks. The superseded 0.4.0 contract, runtime, cadence, and timestamp research remains in Git history at commit `b3a3291`, and its probe source at commit `fb483b4`.
- The f.lux comparison supplies interaction references. Circadia defines its own manual Wake and Bedtime clocks, Daytime ≥ Morning/Evening ≥ Sleep temperatures in kelvin, optional solar targets, transitions that finish by each target, and executable matching. It does not infer Bedtime from f.lux's approximate nine-hour convention.
- The Windows clock research covers skipped/repeated times, elapsed interpolation, half-hour changes, and selected year boundaries. The combined investigation records actual host time-zone and daylight-adjustment changes. The active [Windows clock probe](../../probes/windows-clock/README.md) retains conversion tests and the separately invoked host-setting exercise. Its omission and first-occurrence fixtures do not implement the spec's elapsed-interval adjustment of Wake and Bedtime occurrences. [Clock-change intervals](clock-change-intervals.md) distinguishes that policy from the recorded conversion evidence. The application's Rust schedule tests are separate from these probe results.
- The detailed Reactor checks, first recorded at windows-rs revision `722f202` and rerun on the desktop at the current reference pin, `0496ec1`, verify graph controls, pointer interaction at 100% scaling, settings close/reopen, a native file picker for executables, and foreground lookup. The retained probe's fixed test times and point editor differ from the generated temperature schedule. Settings input validation in the native window, selection of dated Sunrise/Sunset occurrences for schedule targets, and Preview require application verification. Current Preview starts at the current instant and ends at tomorrow's matching local clock, compressed into 1–60 seconds. The UI probe does not verify this playback or the automatic saving of settings edits. The compatibility assessment supplies a dependency-based Windows 11 build 22000 floor; minimum-build execution remains a release check.
- The architecture research supports the selected single Reactor process. The [application tools](../../tools/README.md) separately check resource use and activation through real Windows tray input. The [settings-design rendering probe](../../probes/windows-reactor/settings-design/README.md) rendered the redesigned settings window and tray menu at 100% scaling in the dark and light themes; 150% and 200% scaling, a contrast theme, keyboard use of every page, and screen-reader use remain release checks.
- Session-ending documentation and pinned source support best-effort cleanup in the same process. Actual notification delivery, cleanup during Windows teardown, and the next sign-in's Night Light state remain unverified. Startup can prepare an inactive temperature before enabling Night Light; optical absence of a transient tint is not established. The spec does not adopt the research's direct-enable option: startup prepares 6500 K before enabling Night Light and then runs the ordinary fade, 250 ms by default, to the current target. Quit, and turning Night Light management off, first fade toward 6500 K with the same ordinary fade. A confirmed session end skips the fade. Each of these exits then clears native preview through the settings registry record and turns Night Light off through the separate state record; failure of one does not skip the other.
- Suspend/resume documentation supports current-time reevaluation and separate treatment of timer delivery, elapsed suppression duration, and native output. Windows 11 event ordering and visible Night Light restoration have not been exercised through actual power-state transitions. Reapplying the current temperature after resume even when storage matches is a product requirement, not evidence that Windows always loses its display transform.

### Statements superseded by the settings redesign

The settings redesign changed several product rules that earlier documents restate or recommend against. Those documents keep their dated evidence; the notes below state which statements no longer describe the product. The [spec](../specs/SPEC.md) and its [suppression](../specs/suppression.md), [interface](../specs/interface.md), [localization](../specs/localization.md), and [diagnostics](../specs/diagnostics.md) areas define the current behavior.

- **Automatic saving.** The settings window has no Save, Discard, or close prompt: each valid edit applies to the running schedule and is written automatically, and the last valid settings are what runs. Statements about unsaved drafts, an accepted configuration separate from the draft, Discard, or a Save step describe the earlier model in [Night Light transition control](nightlight-transition-control.md) (unsaved edits controlling output, and Stop or Discard after Preview), [desktop process architecture](desktop-process-architecture.md) (settings owning draft edits), [Windows Reactor UI support](windows-reactor-ui.md) (a live draft and validation for Save), and [combined schedule integration](schedule-integration.md) (unverified Save integration). [Sign-in startup](sign-in-startup.md) registers after Save and keeps close-with-Save open after a failure; Circadia registers or unregisters as soon as the sign-in toggle changes and shows a failure at that toggle. Its measured Run-key and startup-approval results still apply.
- **Preview.** Preview runs while suppression is active and overrides it while playing; suppression that starts during Preview takes effect when Preview ends. Settings edits are disabled while Preview plays, and Circadia draws no tint over the window. The Stop and Discard description in [Night Light transition control](nightlight-transition-control.md) predates these rules.
- **Fades and exit.** One ordinary fade, 250 ms by default and configurable from 100 to 10,000 ms, serves startup, turning management on or off, Quit, suppression start and end, recomputation of the target temperature, corrections of outside changes, and recovery from Night Light read, write, or observation failures; it replaces the separate 1000 ms startup fade. [Windows session shutdown](session-shutdown.md) recommends a single off request without a fade on Quit and a separate startup fade independent of the ordinary fade, and [Night Light transition control](nightlight-transition-control.md) lists the startup fade and the ordinary fade as separate short transitions. Their evidence about short transitions and session notifications still applies, but Quit and turning management off fade toward 6500 K before cleanup; only a confirmed session end stays immediate.
- **Location.** "Use my Windows location" is a saved toggle. While it is on, Circadia requests one position when the toggle is turned on and each time the settings window opens, saves the result as the configured coordinates, keeps the previous coordinates when a request fails or is denied, and never requests a position at startup or in the background. The one-time request described as explicit coordinate acquisition or "Use current location" in [location and solar times](location-and-solar-times.md), [f.lux behavior](flux-behavior.md), [desktop process architecture](desktop-process-architecture.md), and [Windows Reactor UI support](windows-reactor-ui.md) predates the toggle. The documented rule that `RequestAccessAsync` runs on the UI thread while the app is in the foreground still supports requesting only from the open settings window.
- **Tray menu and recent apps.** The recent-app history keeps five distinct executables, and settings lists all five, but the tray menu shows three. The five tray entries in [f.lux behavior](flux-behavior.md) and [Windows Reactor UI support](windows-reactor-ui.md) describe the earlier count. The menu has "Open Circadia settings", the suppression command, a "Suppress while focused" caption, three recent apps marked with a text check mark when listed, and "Quit Circadia". This menu replaces the Settings and Quit actions and the plain-command assumption in [Windows Reactor UI support](windows-reactor-ui.md). [Settings design support](settings-design-support.md) records the menu's Reactor limits.
- **App icons.** Circadia keeps one cached icon per executable file name and stores no executable paths in its configuration. The cache records the path, size, and last-write time of the file each icon was read from, and focus or file selection supplies a newer path. When the recorded file no longer exists and no other path is known, settings keeps showing the cached icon. The recommendations in [executable icons and display names](executable-icons.md) to store each list entry's path, key the cache by path, and show the generic icon for a missing file describe the earlier choice; its measurements and its size and last-write-time check still apply.
- **Log contents.** The local log can record coordinates, executable names, file paths, and window titles, and bug reports remind the user to remove personal data before sharing the log. [Persistent crash logging](crash-logging.md) says that an in-process minidump falls outside the diagnostics rules because it can include such data; that reason no longer applies. Its documented risks of writing a minidump from the crashing process still apply.
- **Graph.** The graph shows hour labels every 3 hours, vertical gridlines, a fill under the curve colored by each hour's temperature, Wake, Sunrise, Sunset, and Bedtime markers, and a now marker, with no point editing. The graph "without numeric labels" in [combined schedule integration](schedule-integration.md) and the axis labels deferred in [Windows Reactor UI support](windows-reactor-ui.md) describe the earlier requirement. That document's 220 sampled rectangles remain evidence and a fallback; the selected approach draws the fill and curve with `windows-canvas` ([Settings design support](settings-design-support.md)).
- **Window structure.** The settings window has four pages in a navigation pane: Schedule, App suppression, Transitions, and General. The scrollable single-window presentation and the optional `NavigationView` in [Windows Reactor UI support](windows-reactor-ui.md) predate this structure.
- **Reactor revision.** Circadia follows windows-rs `master` through one reference pin recorded in [Windows Reactor UI support](windows-reactor-ui.md), which is updated at each bump. Other documents keep the revision they observed, usually `722f202`, as dated evidence. The future `TaskbarCreated` delivery check that [Night Light transition control](nightlight-transition-control.md) names at `722f202` applies to the reference pin in use when it runs.

## Solar evidence and archived scheduling models

The local solar comparison supports the MVP's optional solar calculation. It verifies zero and repeated event counts and agreement with independent references for the recorded fixtures. The Windows location experiment supports obtaining a Windows position on its tested host, which the "Use my Windows location" setting relies on; denied permission, disabled services, cancellation, and production integration remain application checks.

The archived scheduling algorithm adjusts Morning/Evening reference times, chosen from sunrise/sunset or backup clocks, to preserve the order of points placed at offsets from them. A separate editing experiment searches for offsets and positions that place an inserted or dragged point at the requested time while preserving the dated order of other points. These experiments use a broader editing model than the generated three-temperature schedule. Their backup clocks, movable reference times, and arbitrary offsets are not MVP requirements. The recorded results describe that tested model; they do not establish the current rules for selecting Sunrise/Sunset occurrences or generating transitions.

City/address lookup and automatic fullscreen detection remain deferred. Their provider comparisons and detection experiments do not add MVP requirements.

The [source archive](archives/README.md) preserves the solar calculator, scheduling and editing algorithms described above, combined solar harness, published Reactor comparison, and location code. Run those experiments from an extracted snapshot. The active [probe index](../../probes/README.md) lists the pinned Reactor and settings-design rendering probes, and the Windows clock and solar-timing probes.
