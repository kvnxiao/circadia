## Applicability to the MVP

- The 0.5.0 transition research records the current public operations: the native preview flag kept enabled between temperature writes for short changes, plain sets with occasional application refreshes for gradual changes, explicit cleanup, and one lifetime handle with a startup timestamp margin. This native flag differs from Circadia's schedule Preview playback. Circadia does not move timestamps backward, because the upstream probe found that temperature changes after a timestamp rewind were ignored, consistent with Windows ignoring timestamps at or below an inferred highest applied value. Source findings and upstream display observations have separate limits. Controller integration and supported-host visual behavior remain implementation and release checks.
- The 0.4.0 contracts, runtime, cadence, and timestamp documents preserve earlier source inspection and measurements. Their per-step refresh timings, display-derived ceiling, and benchmark recommendations do not define the current MVP. Circadia uses a configurable 1–240 Hz output ceiling and ordinary schedule Preview; it does not acquire monitor refresh rates or provide a benchmark. Earlier measurements are not rewritten as 0.5.0 results. Their probe source is preserved in Git history at commit `fb483b4`; the upstream 0.5.0 probes supersede those probes.
- The timestamp probe adds 328 successful measured refreshes and a human report of smooth visible warming and cooling on the tested host. Native strength and schedule changes passed at large timestamp leads. Native UI on/off at the largest lead and longer accumulation remain release checks; public-library activation and restoration succeeded.
- The f.lux comparison supplies interaction references. Circadia defines its own manual Wake and Bedtime clocks, three ordered temperatures, optional solar targets, transitions that finish by each target, and executable matching. It does not infer Bedtime from f.lux's approximate nine-hour convention.
- The Windows clock research covers skipped/repeated times, elapsed interpolation, half-hour changes, and selected year boundaries. The combined investigation records actual host time-zone and daylight-adjustment changes. The active [Windows clock probe](../../probes/windows-clock/README.md) retains conversion tests and the separately invoked host-setting exercise. Its omission and first-occurrence fixtures do not implement the spec's elapsed-interval adjustment of manual targets. [Clock-change intervals](clock-change-intervals.md) distinguishes that policy from the recorded conversion evidence; native Rust integration remains unverified.
- The recorded Reactor checks verify graph controls, pointer interaction at 100% scaling, settings close/reopen, a native executable dialog, and foreground lookup. The retained probe's fixed fixture anchors and point editor differ from the generated schedule. Native settings validation, solar selection, and Preview still need verification. Current Preview starts at the current instant and ends at tomorrow's matching local clock, compressed into 1–60 seconds. The pinned UI probe does not verify this playback or the live draft lifecycle. The compatibility assessment supplies a dependency-based Windows 11 build 22000 floor; minimum-build execution remains a release check.
- The architecture research supports the selected single Reactor process. Resource measurements, actual Shell activation, broader display scaling, and accessibility remain application checks.
- Session-ending documentation and pinned source support best-effort cleanup in the same process. Actual notification delivery, cleanup during Windows teardown, and the next sign-in's Night Light state remain unverified. Startup can prepare an inactive temperature before enabling Night Light; optical absence of a transient tint is not established. Current exit independently clears native preview through the settings registry record and turns Night Light off through the separate state record. Failure of one does not skip the other.
- Suspend/resume documentation supports current-time reevaluation and separate treatment of timer delivery, elapsed suppression duration, and native output. Windows 11 event ordering and visible Night Light restoration have not been exercised through actual power-state transitions. Reapplying the current temperature after resume even when storage matches is a product requirement, not evidence that Windows always loses its display transform.

## Solar evidence and archived scheduling models

The local solar comparison supports the MVP's optional solar calculation. It verifies zero and repeated event counts and agreement with independent references for the recorded fixtures. The Windows location experiment supports explicit coordinate acquisition on its tested host; denied permission, disabled services, cancellation, and production integration remain application checks.

The archived scheduling algorithm adjusts Morning/Evening reference times, chosen from sunrise/sunset or backup clocks, to preserve the order of points placed at offsets from them. A separate editing experiment searches for offsets and positions that place an inserted or dragged point at the requested time while preserving the dated order of other points. These experiments use a broader editing model than the generated three-temperature schedule. Their backup clocks, movable reference times, and arbitrary offsets are not MVP requirements. The recorded results describe that tested model; they do not establish the current solar-selection or transition rules.

City/address lookup and automatic fullscreen detection remain deferred. Their provider comparisons and detection experiments do not add MVP requirements.

The [source archive](archives/README.md) preserves the solar calculator, scheduling and editing algorithms described above, combined solar harness, published Reactor comparison, and location code. Run those experiments from an extracted snapshot. The active [probe index](../../probes/README.md) lists the pinned Reactor, Windows clock, and solar-timing probes.
